## 現行方針への訂正

初期構想には、仕事の種類やリスクにかかわらず同じ工程を課す規則が含まれていた。
実証後の運用では、要求と変更の境界を保ちながら、不要な待ち時間と長寿命ブランチを作らない規則へ置き換える。

| 旧案 | 判定 | 現行方針 |
|---|---|---|
| 全社Issue、Epic、作業Issue、タスクIssueの固定4階層 | 廃止 | Intake、Work、Task、Businessを用途で使い分ける。親子関係は必要な仕事だけに設定する |
| develop、Epic、作業の2階層ブランチ | 廃止 | 原則として既定ブランチから短命ブランチを作り、一つの変更成果を一つのPRにする |
| `epic/Epic番号-説明`と`feature/Epic番号-作業番号-説明` | 廃止 | `種別/Issue番号-短い英数字の説明-担当者`を使う。`git ar branch`が生成と検証を担当する |
| merge commitへ統一し、squashを禁止する | 廃止 | squash mergeへ統一する。別々に戻したい変更や別々に承認すべき変更はPRを分ける |
| 1PRを400行以内とし、小さいタスクIssueを3件までまとめる | 廃止 | sizeラベルは分割判断の材料に限定する。行数やIssue件数を一律の合否条件にしない |
| CI通過後にPRを作成する | 廃止 | Draftを含むPRは早期共有に使える。必須checkはマージ前に通過させる |
| すべての作業計画をPLが着手前に確認する | 廃止 | 通常変更は担当者が着手できる。権限昇格、重大変更、完了条件が不明な変更だけ確認を求める |
| reviewerを常に一人に固定し、担当者との兼任を禁止する | 廃止 | Issueの予定reviewer、CODEOWNERS、Rulesetを統合する。通常は第三者レビュー、許可済みの軽微変更は本人マージを選べる |
| hotfixはPMだけが開始でき、3営業日以内に事後確認する | 廃止 | 権限を持つ担当者が`merge/emergency`を申請できる。緊急マージ後に事後レビューIssueを自動作成し、翌営業日までに確認する |
| Epicブランチの全組み合わせを毎晩検査する | 廃止 | open PRのconflict、behind、重複ファイルを定期検査する。未commitの変更は`git ar presence`で共有する |
| developの変更をEpicブランチへ自動同期する | 廃止 | behindを通知し、baseの取り込みは担当者が明示的に行う。自動mergeや自動stashは行わない |
| Epicは2週間、タスクは半日から2日と固定する | 廃止 | GitHub ProjectsのSize、開始日、目標日と、Issueの依存関係で管理する。固定日数ではなく滞留と期限超過を観測する |

## 現行運用の最小契約

- GitHub Issuesは要求、完了条件、判断履歴を記録する。
- GitHub Projectsは担当、状態、優先度、予定の正本とし、依存関係はGitHub Issueのnative relationshipに記録する。
- 変更成果はPRにし、Issueと関連付ける。
- 通常変更は`merge/review`、許可済みの軽微変更は`merge/self`、緊急修正は`merge/emergency`を使う。
- 必須checkとマージ条件はGitHub Rulesetと決定的なCIで検証する。
- 人間はTUI、AIと自動化はCLI引数とversion付きJSONを使い、同じvalidatorを通す。
- Slackとカレンダーは通知と操作の窓口であり、独自の状態を正本にしない。

## 全体構造（4階層のissue × 2階層のブランチ）

```
【issue階層】                          【ブランチ階層】
全社issue（部署の大タスク）             main
```

ブランチはmain・developを除き**2階層のみ**（Epicブランチ＋作業ブランチ）。issueが4階層でもブランチは増やさない。

# 後半：詳細

## 1. 通常フローの流れ

```
1. 全社リポジトリに全社issueが立つ（部署ごとの大タスク）
2. PLが製品リポジトリにEpicを作成し、全社issueのsub-issueに紐付け
3. PLがdevelopからEpicブランチを作成
4. PLが作業issue（担当者単位）に分解し、担当者とreviewerをアサイン
5. 担当者がEpicブランチから作業ブランチを作成
6. 担当者が作業issue本文に作業計画（チェックリスト）を記載 → PLが着手前に計画チェック
7. 担当者が計画の項目からタスクissueを随時作成（計画が厳密なら最初に全部立ててもよい）
8. タスクissue単位で実装 → CI通過 → EpicブランチへPR → reviewerレビュー
9. 承認後、担当者がマージしてタスクissueをclose・計画にチェックを入れる（7〜9を繰り返す）
10. 計画の全項目が消化されたら、PLが完了条件と照合して作業issueをclose
11. 全作業issueが閉じたら、PLがEpicブランチで統合動作確認（CI通過）
12. PLがPMをメンションし、要件の言葉でマージ許可を申請
13. 許可が出たらEpicブランチ→developへマージ、Epicをclose、Epicブランチ削除
14. developへの反映はステージングで確認され、PM判断でdevelop→main（本番リリース）
15. 全Epicが終了したら全社issueは閉じられる（必ず閉じるわけではなく部署判断）
```

例外：タスクの規模が大きく修正範囲が広い場合、1つの全社issueに対してEpicを複数立ててよい。

## 2. 役割の詳細

### PM（Reo）

- 要件定義：全社issueとして各部署の大タスクを定義する
- 最終承認：PLからのマージ申請を受け、**要件に当てはまっているか**の観点でEpicブランチ→developのマージを承認する。技術品質は見ない（PLとreviewerの責任）
- リリース判断：develop→mainのマージタイミングを判断する
- hotfixの依頼起点（後述）

### PL（Epicの責任者）

**責任範囲：分解・アサイン・進捗・受け入れ・PM報告の5つ。** コードレビュー自体は責任に含まれない（reviewerを立てる責任はある）。同時に持てるEpicは2〜3個が上限の目安。

1. **引き受け時**：Epicを作成し全社issueに紐付け。本文に「目的（全社issueのどの要件に対応するか）・完了条件・期限（2週間以内）」を書く。developからEpicブランチを作成。2週間を超えそうならEpicを分割する判断をする
2. **分解**：「1人に渡せて2週間以内に終わる塊」＝作業issueまで割る。**ここで止める**（タスクレベルまで割らない）。本文に「対象範囲・完了条件・触ってはいけない範囲」を書き、担当者だけで作業を始められる状態にする
3. **アサイン**：担当者とreviewer（担当者と別の人）を決めて本文に明記。reviewerのデフォルトはPL自身だが、自分が開発する作業issueは必ず他の人を立てる。期限は担当者と相談して決める
4. **計画チェック**：担当者が引き受け時に書いた作業計画を、**着手前に**「この一覧を全部やれば作業issueの完了条件を満たすか（漏れ・逸脱）」の観点で確認する。**全作業issueが対象**（reviewerを兼ねているかどうかは無関係）。原則1作業issueにつき1回・数分〜10分程度。計画が変更されたら再チェック
5. **開発中**：作業計画のチェックボックス消化率（GitHubが「3 of 7 tasks」のように自動表示）とProjectsで進捗を見る。遅延の兆候があれば担当者と相談し、作業issueの分割・再アサインを検討。コンフリクト通知（自動検知）が来たらマージ順序等を調整。要件変更が来たらEpic本文を編集し、作業issue・タスクissueの追加／closeを行う
6. **受け入れ**：全タスクissueが閉じた作業issueを、完了条件と照らして動作レベルで確認しclose（コードは読まない）
7. **出口**：統合動作確認 → PMへ「検索画面で〇〇ができるようになります」レベルの**要件の言葉で**説明してマージ許可を申請 → マージ・close・ブランチ削除

### 担当者

**責任範囲：作業issue単位の品質保証（テスト・動作確認）と進捗報告。** 遅延は発生してからではなく**兆候の時点で**PLに相談する。

1. **引き受け**：作業issueの本文（対象範囲・完了条件）を確認し、不明点はこの時点でPLに質問。**Epicブランチから**作業ブランチを作成（`feature/Epic番号-作業番号-説明`）
2. **計画**：引き受け時に作業issue本文へ作業計画（やる修正の一覧を1行メモの箇条書き・チェックリスト形式）を書き、PLに通知。タスク粒度でなくてよい。この時点で計画が厳密に固まっている場合は、そのまま全項目をタスクissue化してよい
3. **タスクissue作成**：計画の項目から**テンプレート通りに**随時作成（チェックリスト項目はワンクリックでissueに変換できる）、作業issueのsub-issueに紐付け（1個あたり半日〜2日の粒度）。計画を変える場合はチェックリストを編集してPLに通知
4. **開発**：タスクissue単位で実装。テストを書き、CI通過を確認してからEpicブランチへPR（400行以内・小さいタスクissueは3個までまとめ可・本文に`Closes #番号`）。reviewerをメンション
5. **レビュー対応**：指摘には修正で応える。サイズ超過で差し戻されたら分割して再提出
6. **マージ**：承認後、自分でマージしてタスクissueをcloseし、計画にチェックを入れる（マージ実行者を担当者に固定して責任を明確化）
7. **完了**：計画の全項目を消化したら、完了条件を自己チェックしてPLに報告

## 3. ブランチ・PRルール

### ブランチ

| ブランチ | 起点 | 命名 | 寿命 |
|---|---|---|---|
| main | — | — | 永続（本番） |
| develop | main | — | 永続（統合先） |
| Epicブランチ | develop | `epic/Epic番号-説明` | 2週間以内。マージ後削除 |
| 作業ブランチ | Epicブランチ | `feature/Epic番号-作業番号-説明` | 作業issue完了まで。マージ後削除 |

- developがあるプロジェクトはdevelop統合とする。develop→mainはPM判断
- タスクissueにブランチは作らない。担当者は同じ作業ブランチからタスクissueごとにPRを出す（GitHubは前回マージ以降の差分だけを表示するのでPRは小さく保てる）
- **マージ方式は通常マージ（merge commit）に統一。squashマージはリポジトリ設定で無効化する**（同一ブランチからの複数回PRで差分の二重表示や無用なコンフリクトが起きるため）

### PR

- CI通過がPR作成の前提（テスト未通過はマージ不可のブランチ保護を設定）
- 1PR＝差分400行以内が目安。タスクissueとPRは厳密に1:1にせず、小さいタスクissueは3個まで1PRにまとめてよい（`Closes #45, #46`で複数closeできる）
- PRサイズの自動ラベル（`size/S・M・L・XL`）を既製のGitHub Actionで導入。`size/XL`はreviewerが差し戻し可
- reviewer承認 → 担当者がマージ → タスクissueをclose

### コンフリクト対策の自動化

~~「並行するEpic同士が同じファイルを触っていないか」は自動検知に置き換え、PLは通知が来たときの調整だけを行う。~~

- ~~**レベル1（同一ファイル検知）**：各Epicブランチの`git diff --name-only`（developとの差分ファイル一覧）をブランチ間で突き合わせ、重複があればSlack通知。数十行のスクリプトで実現可~~
- **レベル2（実コンフリクト検知）**：`git merge-tree`（実際にマージせず結果だけ計算するコマンド）でアクティブなEpicブランチの全ペアを毎晩シミュレーションし、コンフリクトが出た組み合わせをSlack通知
- **develop→Epicブランチの自動同期**：developに変更が入ったらEpicブランチへ定期的に取り込む。コンフリクト発生時はSlack通知

## 4. hotfix（本番緊急修正）フロー

通常の4階層を通すと遅すぎるため、専用フローを設ける。

```
1. 本番バグの発見者はPMに連絡（依頼の起点は必ずPM）
2. PMが依頼（全社issueの定義に相当）
3. （全社issue・）Epic・タスクissueの定義と修正開発は1人で行ってよい
4. PMがタスクissueの承認とEpicのマージのすべての権限を持つ（最低2人で完結）
5. マージ後、第三者（reviewer）による事後チェックを必須とする——3営業日以内
6. 事後チェック完了後にissueをclose
```

- PMはコードを読めない前提のため、事後チェックが品質の担保になる
