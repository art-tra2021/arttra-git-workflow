## 現行方針への訂正

初期構想の目的は維持するが、情報の保存範囲、閲覧権限、変更リスクに応じた例外を明確にする。

| 旧案の表現 | 判定 | 現行方針 |
|---|---|---|
| 開発に関係する最終情報はすべてGitHubへ残す | 限定 | 非機密の判断要約、完了条件、Issue間の依存関係、決定理由を記録する。秘密情報、個人情報、顧客の機密情報は転記せず、権限管理された正本への参照だけを残す |
| 全社スケジュールを全員が確認できる状態にする | 限定 | GitHub Projectsを予定と状態の正本とし、Slackとカレンダーは権限に応じて必要な範囲だけを表示する |
| 自分で作成し、自分だけで確認して反映できる状態を減らす | 具体化 | 通常変更は第三者レビューを既定とする。自動検証が十分な軽微変更、許可済みのPL判断、緊急修正は監査可能な例外を使う |
| 要件整理からリリース後確認までを一方向に進める | 廃止 | 仕事の種類ごとに工程は変えてよい。背景と完了条件、Projects上の予定と依存、PR、マージ前の必要な検証を共通契約とする |
| 開発体制がリリース権限と本番反映まで統一する | 分離 | GitHub側はマージ可能な成果物までを扱う。CD、デプロイ、ロールバックは各プロジェクトの運用規則に委ねる |
| 変更の影響範囲を把握する | 具体化 | CI、CODEOWNERS、重複ファイル、依存関係から判断材料を提示する。未知の影響を完全に検出できるとは扱わない |

## 現行運用の共通条件

- Issueには背景と完了条件を記録する。
- 担当、状態、優先度、目標日はGitHub Projectsで管理し、依存関係はGitHub Issueのnative relationshipに記録する。
- コード、営業資料、契約条件、運用手順などの変更成果はPRで管理する。
- マージ前に、その変更へ必要な自動検証と承認を完了する。
- 通常変更は第三者レビューを既定とし、本人マージと緊急マージはIssue時点で明示して監査する。
- SlackとカレンダーはGitHub Projectsの入出力窓口とし、情報を独自に複製して正本化しない。
- 閲覧と操作は最小権限で与え、機密情報をIssue、PR、AI入力へ自動転記しない。
- CDは各プロジェクトで設計し、共通Git運用の対象外とする。
